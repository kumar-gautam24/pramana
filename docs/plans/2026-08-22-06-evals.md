# Pramana Plan 06 — Evals

> **Written retroactively, 2026-08-22.** Built in the same pass as plan 05 rather than planned
> first; this records what exists and why. Every checkbox is done. The value is in the
> decisions and the deferrals, not the sequence.

**Goal:** Turn "does it work" into a number with a unit. `evals` (8003) owns the golden set,
runs it through the real pipeline, and scores what comes back at two levels.

**Why this service is not optional.** California requires AI tools used in coverage decisions
to be periodically assessed for accuracy. The eval harness is a legal obligation before it is
an engineering convenience, which is why a run records everything needed to repeat it.

**Architecture:** FastAPI over `pramana_evals`, layered `routers → services → repositories →
models` with the scoring maths pure in `domain/scoring.py`. It submits cases to `adjudication`
over HTTP like any other client — it has no privileged path in.

## Global constraints

- Database per service; raw SQL; numbered migrations.
- **Golden-case labels are human-authored** ([ADR-0008](../decisions/0008-human-authored-golden-labels.md)).
  A model grading a model measures agreement, not correctness, and would void every number this
  service produces.
- **The schema must not be able to express a denial.** A golden case expecting one would be a
  test for behaviour that must never exist ([ADR-0002](../decisions/0002-no-deny-path.md)).
- Comments explain **why**, never what. Commits: conventional, lowercase imperative, **never any
  attribution trailer.**

### Task 1: Schema

**Files:** `migrations/0001_golden_cases_and_runs.sql`, `src/evals/models/`.

```
golden_cases  id, fixture jsonb, expected_outcome CHECK(approve|escalate),
              expected_criteria jsonb, author NOT NULL, notes, created_at
eval_runs     id, model, prompt_version, thresholds jsonb, git_sha,
              ablation CHECK(none|model_arithmetic), status, started_at, finished_at
eval_results  id, run_id, golden_case_id, case_id uuid, outcome NULL-able,
              reason, criterion_scores jsonb, error, created_at
              UNIQUE (run_id, golden_case_id)
```

- [x] **`fixture` is jsonb, not columns.** This service does not interpret a case, it forwards
  one; mirroring adjudication's request schema here would be two definitions of one contract,
  drifting apart the day a field is added.
- [x] **`expected_outcome` is a two-value CHECK.** The eval schema is structurally incapable of
  expecting a denial.
- [x] **`author` is NOT NULL.** Authorship cannot be omitted and later assumed. ADR-0008 is a
  claim about where labels came from, and a nullable column would make it unverifiable.
- [x] **`eval_results.outcome` is nullable** where `golden_cases.expected_outcome` is not. A case
  that never got a determination — rate-limited, upstream down — has no outcome, and writing
  `escalate` there would silently count an infrastructure failure as a correct refusal.
- [x] **`UNIQUE (run_id, golden_case_id)`.** A retried case updates its row rather than adding a
  second; otherwise the denominator of every rate silently grows.
- [x] **`eval_runs` records model, prompt version, thresholds, git sha and ablation.** An
  assessment whose conditions were not recorded cannot be repeated, and an unrepeatable
  measurement is not evidence. A run and its ablated twin differ in one column and nothing else,
  which is what makes the comparison an argument rather than an anecdote.

### Task 2: The runner

**Files:** `src/evals/services/{runner,adjudication_client}.py`, `src/evals/routers/eval_runs.py`.

- [x] **Cases run one at a time, paced.** Not timidity about concurrency: each case costs
  several model calls against a rate-limited provider, and a run that saturates the limit
  measures the token budget rather than the system.
- [x] **A case that never settles is recorded with `outcome = NULL` and its reason, and the run
  continues.** Folding an unreachable case into `escalate` would let an outage read as a correct
  refusal — the one way this harness could flatter the system it exists to audit.
- [x] **Outcomes are read from the case's own event log**, the same append-only trail an auditor
  would read, rather than from a side channel.
- [x] **A case's confidence is the *minimum* across its criteria.** The gate approves only when
  every criterion clears the bar, so the weakest link is the value a threshold sweep must vary
  against.

---

### Task 3: Scoring

**Files:** `src/evals/domain/scoring.py`.

- [x] **Two levels, because one is not enough.** Criterion-level numbers say whether the system
  read the policy correctly; case-level numbers say what being wrong costs. A project reporting
  only the first is measuring its own machinery; one reporting only the second cannot say why it
  scored as it did.
- [x] **`ConfusionCounts` is deliberately not a 2×2 matrix.** The cells are not symmetric: a
  wrong approval costs money, a wrong escalation costs time, and there is no third error because
  there is no deny path. `unfinished` is separate from all of them.
- [x] **Every money figure is a count times a rate**, never a bare score, so it carries its unit
  by construction.
- [x] **The threshold is applied in scoring, not only in the gate**, so one run can be scored at
  many thresholds without re-adjudicating anything. That is what makes the sweep affordable.
- [x] **The auto-approval denominator is decided cases, not all cases.** A rate computed over
  cases the harness never finished would fall when the provider rate-limits us, reading as the
  system becoming more cautious when nothing about it changed.
- [x] **Sweep ties break toward the higher threshold.** Two thresholds costing the same are not
  equally good — the stricter one approves less on the same evidence, and when the error it
  avoids affects someone's care, the tie must not be settled by list order.
- [x] **Extraction is precision and recall, not accuracy.** Missing a criterion the policy
  contains can produce a wrongful approval; inventing one can only produce a wrongful escalation.
  A single number would hide which direction the system errs in, and they do not cost the same.

## Verified by running it

One real run through the live stack: **3 cases scored, $0 wrongly approved, $72 of
wrongly-escalated clinician time.** That asymmetry — the thing this project exists to argue
about — measured rather than asserted.

## Deferred out of this plan, with an owner

- ~~**The `model_arithmetic` ablation returns 501.**~~ **Closed 2026-08-22, ADR-0021.**
  `adjudication` now has the run mode: `cases.run_mode` selects who performs the threshold,
  category and date comparisons, and the difference between the two arms lives in exactly one
  module. `runner` submits every case with the run mode its run's `ablation` maps to, through a
  one-entry-per-member table, so an `Ablation` value added without a run mode fails when the run
  starts rather than adjudicating everything the ordinary way while the column claims otherwise.
  Two consequences for this service, both new: `report` publishes `ablation_coverage`, because
  `condition_codes` criteria have no comparison to hand to a model and a partial ablation
  reported as a whole one would overstate the experiment; and `POST /golden-cases` now rejects a
  fixture carrying `run_mode` or `idempotency_key`, the second because it would hand a run and
  its ablated twin the same adjudication case and read as perfect agreement.
  A third consequence, added the same day: `GET /eval-runs/{id}/comparison?against={other}`,
  because two report pages diffed by eye is not a measurement. It refuses to produce a delta
  for two runs that differ in more than their ablation — returning both runs' own figures and
  naming the offending fields — and computes everything over the golden cases *both* runs
  decided, so a run that gave up on its hardest cases cannot look cheaper than the run that
  finished them.
  **Still not run.** The apparatus exists and no number does.
- **The golden set is three cases against a design target of sixty**, of which at least twenty
  must escalate and at least eight be near-miss ([ADR-0009](../decisions/0009-near-miss-cases-required.md)).
  Authoring those is human work by definition and cannot be delegated to a model.
- **No test suite.** Built under an instruction to skip test-writing. `domain/scoring.py` is pure
  and is the part a reviewer should read first, which also makes it the cheapest thing in the
  project to test properly. **Owner: whoever next touches this service.**
- **The report's cost figures now travel with their rates.** `report` returns `costs` alongside
  every money figure, because the console renders each as a count times a rate and a total
  nobody can decompose is a number to be believed rather than checked. Added 2026-08-22.
- **Criterion-level scoring has never been exercised against a populated
  `expected_criteria`.** The matching is a normalised word-overlap heuristic with a threshold;
  whether that heuristic is good enough is itself unmeasured.

## Self-review

**Coverage.** Implements the design's §7 evaluation section and the `evals` service row. Does not
cover: auth and gateway (plan 05), the console (plan 07).

**The risk this work carries.** An eval harness that flatters the system it audits is worse than
none, because it produces numbers people act on. Three defences are structural rather than
procedural: a schema that cannot express a denial, an unfinished case that cannot be counted as a
refusal, and an author column that cannot be null. The undefended edge is the size of the golden
set — three cases is a demonstration that the number has units, not a measurement of anything —
and the README says so in those words.
